## Мессенджер с групповыми чатами

**Мессенджер** - сервис для обмена текстовыми сообщениями, картинками, фото- и видео-файлами между пользователями, через локальную сеть или интернет.  
> Далее по тексту будет принята следующая терминология:  
> **Сообщение** - любые данные, атомарно передаваемые между пользователями в поддерживаемых форматах, например, текстовое, видео, PNG и т.п.  
> **Диалог** - обмен информацией между двумя пользователями (с поддержкой истории и других сервисов). Введено для того чтобы как-то различать маршруты точка-точка и точка-многоточка (групповая рассылка).

Предполагается разработка приложений для мобильных ОС (Android, iOS) и web-страницы.

Система относительно большая, рассчитанная на средних размеров страну (регион), скорее всего несколько часовых поясов.  
Оценка масштаба (больше информации в разделе "сайзинг"):

| Показатель | Значение | Примечание |
| ---------- | -------- | ---------- |
| Зарегистрированных пользователей | 100_000_000 | |
| DAU | 20_000_000 | 20 % от зарегистрированных |
| MAU | 40_000_000 | Для мессенджеров типичное значение отношения DAU/MAU (его еще называют коэффициентом «липкости», stickiness ratio) обычно лежит в диапазоне 40–60% |
| Исходящих сообщений от пользователя в сутки | 15 | Текст, медиа |
| Всего исходящих сообщений в сутки | 15 * 20_000_000 = 300_000_000 | Текст, медиа |
| Доля медиа | 10%, средний объект 400 КБ | Фото/файлы |
| Пик исходящих сообщений | ×5 к среднему | Час пик будет размазан если часовых поясов несколько |
| Пик одновременных пользователей | 4_000_000 | 20 % DAU |
| Средний RPS | 300_000_000 / 86_400 ≈ 3_500 (3_472) | |
| Пиковый RPS | 3_500 * 5 = 17_500 | х5 от среднего RPS |
| Объем медиа в сутки | 300_000_000 * 0.1 * 400 kB = 12 ТБ | |
| Объем медиа в год | 12 TB * 365 ≈ 4.5 (4.38) ПБ | Без учета дедупликации и уборки мусора |

### 2.3 Описание компонентов

#### 2.3.1 API Gateway

Единая точка входа для всех клиентских запросов. Принимает клиентский HTTPS и WSS, проверяет сессию через **Authentication Service**, маршрутизирует в сервисы. Долгие сокеты и heartbeat (каждые 15 с) заканчиваются здесь. Админский HTTPS идет в Maintenance отдельно.

#### 2.3.2 Authentication Service + Auth DB

Сервис аутентификации пользователей со своей отдельной базой данных. Поддерживает до 10 сессий на каждого пользователя. Вход по email, письма через **SMTP Service**.

#### 2.3.3 Presence Service + Redis

Сервис присутствия хранит online/offline устройств в Redis по факту WSS heartbeat с Gateway. Нет ping 120 с - статус устаревает. Сам на устройства ничего не рассылает.

#### 2.3.4 Message Service + DB + Object storage + Холодное хранилище

Принимает, хранит и отвечает за рассылку сообщений (диалог и группа ≤256): история, статусы, реакции, edit/delete/reply/пересылка. Текст и метаданные - в своей БД, файлы до 100 МБ - в object storage.

#### 2.3.5 Contact Service + DB

Каталог пользователей, книга контактов (до 5000), блокировки, поиск; метаданные групп и членство, инвайты только от админа группы.

#### 2.3.6 Push Service

Сервис взаимодействия со службами Apple и Google для отправки PUSH-уведомлений. Также поддерживает отправку уведомлений для web. Обработка mute.

#### 2.3.7 Maintenance Service + DB

Сервис поддержки функций администрирования и мониторинга. Админ-API и аудит; метрики - отдельный контур.

#### 2.3.8 SMTP Service

Внутренний адаптер для взаимодействия с почтовыми серверами.

### 2.4 Обоснование архитектурного стиля

Стиль: клиент–сервер за API Gateway плюс несколько независимо масштабируемых сервисов (не модульный монолит и не «микросервисы на каждый метод»).  
Нагрузка неоднородна, один процесс не масштабирует ее одинаково:

| Сервис | Требования/ограничения | Как масштабируем |
| ------ | ---------------------- | ---------------- |
| Gateway | до ~4 млн WSS (20% от DAU), ping 15 с | горизонтально, sticky-сессии |
| Message | ≥ 20_000 RPS send + рассылка в группы ≤256 | шарды по chat_id |
| Object storage | ~12 ТБ/сутки | отдельный бакет, горячее/холодное |
| Presence | last-seen, не каждый ping | Redis, запись реже keepalive |
| Push | офлайн, вендоры | свой пул воркеров |

Монолит с общей БД на этом профиле смешает 4 млн сокетов, 4.5 ПБ медиафайлов и историю сообщений в одном сервисе. Система из 15–20 сервисов при 20_000 RPS send не окупается: лишние связи/протоколы обмена, сложнее.

### 2.5 ADR (Architecture Decision Record)

#### Realtime-канал: WebSocket на API Gateway

- **Контекст:** в пике около 4_000_000 (20% от DAU, 20_000_000 * 0.2 = 4_000_000) одновременно открытых клиентов. Heartbeat - каждые 15 с (nF4). Статус присутствия устаревает через 120 с (nF5). Канал нужен для входящих сообщений, статусов, реакций и presence.

| Вариант | Оценка |
| --- | --- |
| HTTP long-polling | 4_000_000 / 15 с ≈ 267_000 (266 667) запросов/с только на keepalive, каждый со своим разбором HTTP. На пике это больше нагрузки, чем send (nF1 = 20_000 RPS) |
| SSE (Server-Sent Events) | Удобен для сервер-клиент, отдельный канал все равно нужен для send и ping |
| Прямой TCP/собственный протокол | Меньше накладных расходов, но свой клиент, балансировка и TLS на трех платформах |
| WSS до Gateway | Один долгий сокет на устройство: ping, входящие события и исходящий send идут в нем. HTTP остается для логина, профиля, контактов и выдачи URL медиа |

- **Решение:** клиент держит WSS на API Gateway. Балансировщик привязывает соединение к инстансу (sticky). Ping 15 с заканчивается на Gateway и в Presence, Message и БД не пишется. Входящие события Gateway получает от Message и пишет в уже открытый сокет.
- **Следствия:** Gateway масштабируется числом сокетов, не RPS send.

#### Одна запись сообщения на чат (курсор), файл - в object storage

- **Контекст:** 300_000_000 исходящих сообщений в сутки, пик send 17_500 RPS, потолок группы 256 (nF8), файл до 100 МБ (nF9), медиа ≈ 12 ТБ/сутки и ≈ 4.38 ПБ/год. История читается с любого из ≤ 10 устройств.

| Вариант | Оценка |
| --- | --- |
| Копия сообщения на каждого получателя | Запись раздувается в число участников. При средней группе 32 участника и доле групповых 20 % это около ×7 к записи (0.8 × 1 + 0.2 × 32 = 7.2) |
| Файл в той же БД, что и текст | 12 ТБ/сутки и объекты по 100 МБ попадают в WAL, реплики и бэкапы БД сообщений |
| Одна строка на `chat_id` + объект в бакете | Текст и метаданные пишутся один раз. Файл уходит в object storage, в строке остаются ключ, размер и хеш. Шард выбирается по `hash(chat_id)`, поэтому история одного чата не размазана по узлам |

- **Решение:** Message хранит сообщение один раз в шарде чата. Клиент забирает файл прямым HTTPS GET из object storage. Горячий бакет - 30 суток, дальше lifecycle уносит объект в холодный класс; Message этот перенос не делает. Прочтение диалога хранится на сообщении (доставлено / прочитано). Прочтение группы - курсор `(user_id, chat_id, last_read_msg_id)`, без строки на каждого участника и каждое сообщение.
- **Следствия:** диск БД сообщений считается от 300 млн строк в сутки, а не от fan-out. Емкость шарда упирается в горячие чаты: всплеск одного чата до 256 живых получателей остается на одном шарде, средний fan-out им не является. Потолок 256 ограничивает одиночную рассылку. Удаление и правка - обновление одной строки и, для файла, отдельная политика объекта.

> **Курсор** - это способ хранить «прочитано» в группе одной отметкой на человека, а не отдельным статусом у каждого сообщения.  
> В диалоге получатель один, поэтому флаги «доставлено» и «прочитано» лежат прямо на строке сообщения. В группе участников до 256, и та же схема дала бы строку на каждую пару «участник × сообщение».  
> Курсор — одна строка на пару (chat_id, user_id) с одним числом last_read_msg_id: «этот человек дочитал чат до этого сообщения». msg_id в чате растет по порядку, поэтому все с номером не больше курсора считается прочитанным.  
> Группа из 32 человек и 1 000 сообщений:
>
> | Как хранить | Сколько строк |
> | ----------- | ------------- |
> | Статус на каждого участника и каждое сообщение | 32 × 1_000 = 32_000 |
> | Курсор | 32 |
>
> Новое сообщение новых строк не добавляет. Когда человек дочитывает, обновляется одно число в его курсоре.

> **Fan-out** — это размножение одного события на многих получателей. Одно отправленное сообщение «раскрывается веером» в доставку каждому адресату.

#### Presence: редкий last-seen в Redis

- **Контекст:** 267_000 ping/с при 4 млн сокетов. Сервис присутствия показывает online/offline и не рассылает события сам. Данные старше 120 с устаревают.

| Вариант | Оценка |
| --- | --- |
| Писать каждый ping в Presence | 267_000 записей/с, из них почти все не меняют статус |
| Хранить presence в БД сообщений | Короткоживущие ключи с TTL 120 с смешиваются с историей, которую храним год |
| Redis, запись не чаще раза в 60 с | Gateway коалесцирует ping и обновляет last-seen. Ключ на устройство, TTL 120 с: одна пропущенная запись еще не переводит пользователя в offline |

- **Решение:** Redis хранит статус устройств, которые сейчас на связи. Предположим, что 256 байт - круглая верхняя оценка на ключ, тогда объем данных - около 1 ГБ на 4 млн ключей (4_000_000 * 256 = 1_024_000_000 байт), поэтому кластер берется ради двух зон (резервирование), а не ради объема. Офлайн-доставка в этот контур не входит: ее делает Push Service.
- **Следствия:** отказ Redis гасит индикатор присутствия и не блокирует send и историю. После гибели Gateway ключи доживают до TTL и гаснут сами.

## 3. Сайзинг

Доминируют не 3_500 (3_472) RPS send, а три вещи:

- fan-out получателей
- исходящий трафик медиа
- год хранения объектов

Ниже send доведен до порога nF1 (20_000 RPS). Две зоны доступности (два сервиса мессенджера в целом) в одном регионе; потеря одной зоны не снижает пиковую емкость сокетов и чтение истории.

> **Зона доступности** — отдельная площадка дата-центра со своим питанием и сетью. Регион один, зоны две. Сервисы стоят в обеих, чтобы отказ одной не останавливал систему.

### 3.1 Допущения

Исходные цифры (DAU, 15 сообщений, ×5, 10 % медиа, 400 КБ, 12 ТБ/сутки) - из введения.

| ID | Допущение |
| --- | --- |
| A1 | Пик одновременных пользователей = 20 % DAU = 4_000_000. Несколько часовых поясов уже учтены множителем ×5 к среднему send |
| A2 | Один живой WSS на online-пользователя. Фоновое устройство получает push |
| A3 | 80 % сообщений - диалог, 20 % - группа |
| A4 | Средний размер группы G = 32. Потолок nF8 = 256 - предел одной рассылки, не среднее |
| A5 | В пике живой сокет есть у 25 % адресатов |
| A6 | В БД на сообщение приходится 1 КБ: строка, индексы, служебные поля. Средний текст много меньше лимита 4096 символов |
| A7 | Ретеншн (время хранения записи) текста - 1 год в первичной БД. Медиа: 30 суток горячие, остаток года - холодные. Дедупликация и сборка мусора не заложены |
| A8 | На один медиаобъект в среднем 4.4 скачивания: диалог ×1.5, группа - половина из 32 участников |
| A9 | Шард сообщений в расчете держит 2_000 записей/с и 5_000 чтений/с на primary. Движок БД выбирается в разделе 4, бюджет тот же |
| A10 | Чтение истории: среднее ≈ 8_000 RPS, пик (открытие приложения) = 60_000 RPS. Пик - около 15 чтений/с на 1_000 online |
| A11 | Средний размер книги контактов: 150 записей |

Исходя из того, что: 80 % - диалоги, 20 % группы (32 участника в среднем) см. A3 и A4, коэффициент получателей на одно отправленное сообщение:

```text  
A_fan = 0.8 × 1 + 0.2 × 32 = 7.2
```

### 3.2 RPS

**Вход send** (уже посчитан во введении):

```text
RPS_avg  = 300_000_000 / 86_400 ≈ 3_500 (3_472)
RPS_peak = 3_500 × 5 = 17_500   # как во введении: от округленного среднего
RPS_cap  = 20_000               # nF1, запас ≈ 14 % к пику 17_500
```

**Соединения и ping** - нагрузка Gateway:

```text
C_peak   = 0.2 × 20_000_000 = 4_000_000
Ping_RPS = 4_000_000 / 15 ≈ 267_000
Presence = 4_000_000 / 60 ≈ 66_700 записей/с в Redis
```

**Получатели** Одно сообщение порождает `A_fan` адресатов (см. п. 3.1). В пике расчетного send:

```text
R_peak = 17_500 × 7.2 = 126_000 адресатов/с
WSS    = 126_000 × 0.25 = 31_500 событий/с в открытые сокеты
Push   = 126_000 × 0.75 = 94_500 уведомлений/с вендорам
```

На пороге nF1 (20_000 RPS) те же доли дают 144_000 адресатов/с, 36_000 событий WSS/с и 108_000 push/с. Push стоит в очереди и не удлиняет прием send: вендоры вне nF3.

**Запись в БД сообщений** - одна строка на сообщение плюс статусы диалога, без строки на каждого участника группы:

```text
W_msg    = 20_000 вставок/с
W_status = 20_000 × 0.8 × 2 = 32_000 обновлений статуса диалога/с
W_sum    = 52_000 записей/с
```

Курсоры прочтения групп сидят на чтении истории, а не на fan-out.

**Чтение:** пик 60_000 RPS истории, среднее ≈ 8_000 RPS. Логин, контакты и поиск на этом фоне малы: десятки–сотни RPS. Поиск по 100 млн профилей вынесен отдельно и в бюджет send не входит.

**Шарды:**

```text
N_shards = ceil(52_000 / 2_000) = 26  →  берем 32
```

На шард приходится ≈ 1_600 записей/с и, на пике чтения, 60_000 / 32 ≈ 1_900 RPS. Чтение закрывают реплики. 26 шардов упираются в потолок A9 (2_000 записей/с на primary). 32 - ближайшая степень двойки: потолок около 64_000 записей/с, выше суммы 52_000.

### 3.3 Хранилище

**Текст и метаданные, 1 год, с индексами:**

```text
300_000_000 × 1 КБ = 300 ГБ/сутки
300 × 365 = 109.5 ТБ логически
109.5 × 3 реплики ≈ 329 ТБ диска на кластер
```

На шард 109.5 ТБ / 32 ≈ 3.42 ТБ. С WAL и запасом - диск **6 ТБ** на узел (итого с учетом реплик 96 дисков).

**Медиа, без дедупликации:**

```text
сутки     = 12 ТБ
год       = 12 × 365 = 4_380 ТБ ≈ 4.38 ПБ
горячее   = 30 × 12 = 360 ТБ               # Первые 30 суток объект лежит в дорогом быстром хранилище
холодное  = 4_380 - 360 = 4_020 ТБ         # Дальше политика бакета сама переносит его в более дешевый архив
```

Репликацию объектов дает класс хранения бакета, в диск БД она не входит.

**Прочие контуры** (к году сообщений не прибавляются):

| Данные | Оценка | Куда |
| --- | --- | --- |
| Учетки, 100_000_000 × ~1 КБ | ≈ 100 ГБ | Auth DB, 1 primary + 2 реплики |
| Сессии, до 10 устройств | порядка 100 ГБ | Auth DB |
| Книги контактов, в среднем ~150 (A11) из лимита 5_000 | порядка 2 ТБ с репликами (см. примечание ниже) | Contact DB |
| Presence, 4 млн ключей × ~256 Б | ≈ 1 ГБ | Redis; шесть узлов нужны для двух зон |

> Пояснение о размере БД под книги контактов  
> 100_000_000 пользователей × 150 (A11) контактов = 15_000_000_000 записей  
> 15_000_000_000 записей × 45 Б × 3 реплики ≈ 2.0 ТБ  
> 45 Байт - структура записи в книге контактов, примерно:
>
> | Поле | Зачем | Байт |
> | ---- | ----- | ---- |
> | user_id | чей это контакт, int64 | 8 |
> | contact_id | кого добавили, int64 | 8 |
> | flags | блокировка, mute, избранное, int32 | 4 |
> | created_at | когда добавили, int64 | 8 |
> | индекс (user_id, contact_id) | доля ключа и заголовка btree | 17 |
> | **Итого** | | 45 |
>
> Имя, аватар и статус «в сети» в эти 45 байт не входят: имя лежит в профиле, присутствие — в Redis.

### 3.4 Bandwidth

Медиа, 400 КБ на объект, 10 % сообщений:

```text
B_in_avg  = 12 ТБ / 86_400 ≈ 139 МБ/с ≈ 1.1 Гбит/с
B_in_peak = 17_500 × 0.1 × 400 КБ = 700 МБ/с ≈ 5.6 Гбит/с
m_down    = 0.8 × 1.5 + 0.2 × 32 × 0.5 = 4.4            # сколько раз один файл скачивают, в группах файл открывает половина
B_out_avg = 139 × 4.4 ≈ 610 МБ/с ≈ 4.9 Гбит/с
B_out_peak ≈ 700 × 4.4 = 3_080 МБ/с ≈ 24.6 Гбит/с
```

За месяц наружу уходит ≈ 610 МБ/с × 86_400 × 30 ≈ **1_600 ТБ** исходящего трафика.

Рядом с этим служебный трафик маленький: ping 267_000/с по короткому кадру - порядка 100 Мбит/с, репликация БД сообщений ≈ 52_000 × 1 КБ ≈ 52 МБ/с. Канал наружу задает медиа, не сокеты.

### 3.5 Ресурсы

Ориентир на узел Gateway - 50_000 спокойных сокетов (ping раз в 15 с, редкие кадры сообщений). Память на сокет порядка десятков килобайт: 50_000 × 32 КБ ≈ 1.6 ГБ, поэтому 8 ГБ на инстанс достаточны.

Чтобы пик в 4 млн сокетов пережил потерю одной зоны, с запасом 20 %:

```text
N_az = ceil(4_000_000 × 1.2 / 50_000) = 96
N_gw = 96 × 2 зоны = 192
```

| Компонент | Узлы | Профиль | Зачем столько |
| --- | --- | --- | --- |
| API Gateway | 192 (96 × 2 зоны) | 4 vCPU, 8 ГБ | 4.8 млн сокетов на зону |
| Message (без БД) | 32 | 4 vCPU, 8 ГБ | по узлу на шард: прием 20_000 RPS и 36_000 событий/с в Gateway |
| БД сообщений | 96 = 32 шарда × (1 primary + 2 replica) | 8 vCPU, 32 ГБ, 6 ТБ NVMe | 52_000 записей/с, 109.5 ТБ логически, чтение с реплик |
| Redis presence | 6 | 2 vCPU, 8 ГБ | 66_700 записей/с, датасет ≈ 1 ГБ, две зоны |
| Push workers | 64 постоянно, до ~160 в пике | 2 vCPU, 4 ГБ | пик ≈ 108_000 push/с, очередь сглаживает вендоров |
| Auth, Contact, SMTP, Maintenance | ≈ 12 | 4 vCPU, 8 ГБ | RPS далеко ниже send; Contact DB - отдельная тройка реплик внутри этой оценки |
| Object storage | бакет | 360 ТБ hot + 4_020 ТБ cold | PUT пик 1_750 объектов/с, GET пик по множителю 4.4 |

Итого по счету виртуальных ядер примерно: Gateway 768, БД сообщений 768, остальной прикладной слой около 320. Диск, который покупается явно, - **576 ТБ NVMe** у БД сообщений (96 × 6 ТБ). Медиа в эту сумму не входит.

## 4. Хранение данных

Движки выбраны под бюджет раздела 3: 32 шарда сообщений (primary и две реплики), Auth и Contact отдельными тройками, presence в Redis. Новый кластер в стоимость не добавляется.

### 4.1 Выбор БД

| Контур | Движок | Почему этот |
| --- | --- | --- |
| Сообщения | PostgreSQL, 32 независимых кластера | Одна строка на сообщение, UPDATE правки и удаления, уникальность повторной отправки. На шард ≈ 1_600 записей/с и ≈ 1_900 чтений/с при бюджете A9 2_000 / 5_000 |
| Учет и сессии | PostgreSQL, 1 primary + 2 реплики | ≈ 100 ГБ учеток и порядка 100 ГБ сессий. Запись редкая относительно send |
| Контакты, группы, список чатов | PostgreSQL, 1 primary + 2 реплики | Порядка 2 ТБ с репликами, десятки–сотни RPS. Два индекса покрывают оба запроса |
| Поиск пользователей | Тот же Contact/Auth, индекс по префиксу имени | 100 млн профилей, десятки–сотни RPS, вне бюджета send. Отдельный поисковый кластер не заводим |
| Presence | Redis | TTL 120 с, датасет ≈ 1 ГБ. Отказ гасит индикатор и не трогает историю |
| Файлы | S3-совместимый бакет | Объект не попадает в WAL БД. Горячий класс 30 суток, дальше lifecycle |
| Аудит | PostgreSQL у Maintenance | Малый объем, тот же тип, что у Auth |

Сообщения не кладем в Cassandra или Scylla. Сайзинг уже расписан как primary и две реплики со чтением с реплики; у широкой колонки нет этого primary, и 96 узлов пришлось бы считать заново. Правка и удаление в ADR - обновление одной строки, в PostgreSQL это обычный UPDATE.

Один общий PostgreSQL на все сообщения не берем: 52_000 записей/с и 109.5 ТБ логически выходят за узел, который в A9 держит 2_000 записей/с.

Файл в ту же БД не кладем: 12 ТБ/сутки и объекты до 100 МБ раздувают WAL и реплики. В строке сообщения остаются ключ, размер и хеш. Дедупликация по хешу в 4.38 ПБ не входит (A7).

Реакция, правка и удаление - UPDATE той же строки на шарде чата. Даже если реакция есть у каждого десятого сообщения на пороге nF1, это +2_000 UPDATE/с к уже посчитанным 52_000. Потолок 32 шардов, 64_000 записей/с, заново не выбирается.

### 4.2 Шардирование

Ключ сообщения:

```text
shard = hash(chat_id) % 32
```

История одного чата лежит на одном primary. Ключ user_id размазал бы группу по шардам и вернул бы fan-out записи, от которого отказались в ADR. 32 - степень двойки из раздела 3: следующий шаг - 64 шарда и перенос половины диапазона хеша, а не переразбиение произвольных 26.

На шарде чата:

| Таблица | Ключ | Зачем |
| ------- | ---- | ----- |
| messages | (chat_id, msg_id) | Текст, ключ объекта, reply, флаги правки и удаления. В диалоге здесь же «доставлено» и «прочитано» |
| group_read_cursors | (chat_id, user_id) | Курсор (last_read_msg_id), без строки на каждого участника и каждое сообщение |
| Уникальность отправки | (chat_id, sender_id, client_msg_id) | Повтор send с тем же id возвращает уже записанный msg_id |

msg_id выдает primary в той же транзакции, что и INSERT, из счетчика этого чата. Порядок в чате - порядок коммитов на этом primary. Горячий чат сериализуется на одной строке счетчика: люди в группе из 256 не делают 2_000 send/с, в потолок шарда упирается сумма чатов.

Список чатов пользователя, книга контактов и состав группы в эти шарды не входят. Их держит Contact DB без своего шардирования:

| Запрос | Индекс |
| ------ | ------ |
| Мои контакты, мои чаты, блок | (user_id, …) |
| Участники группы для рассылки | (chat_id, user_id) |

chat_id диалога один на пару пользователей, chat_id группы выдает Contact при создании. Клиент берет список чатов из Contact, а страницу истории - с одного шарда по уже известному chat_id.

Внутри шарда таблица messages режется по месяцу. 300 ГБ/сутки на кластер - это ≈ 9.4 ГБ/сутки на шард и ≈ 280 ГБ за месяц. Год хранения - отсоединить 12-ю партицию, а не удалять сотни миллионов строк.

Реплики шарда, две зоны:

| Узел | Зона | Роль |
| ---- | ---- | ---- |
| Primary | AZ1 | Запись, выдача msg_id |
| Sync-реплика | AZ2 | Подтверждение send ждет ее WAL |
| Async-реплика | AZ1 | Чтение истории, primary не грузим |

Пик чтения шарда ≈ 1_900 RPS при бюджете 5_000. После потери одной зоны оставшийся узел это чтение закрывает. Сообщение, на которое клиент получил ack, есть на primary и в другой зоне. Потерянный ack клиент повторяет тем же client_msg_id.

### 4.3 Кэширование

Кэш не заменяет БД сообщений. Страницы истории не кладем в Redis presence: по ADR отказ Redis гасит только индикатор.

| Данные | Где | Ключ и сброс |
| ------ | --- | ------------ |
| Страница истории старше хвоста | Память процесса Message | (chat_id, before_msg_id). Страница не меняется, сбрасывать нечего |
| Хвост чата | Память процесса Message | (chat_id, latest), сброс на INSERT этого чата |
| Состав группы и блок | Память Message на пути send | Сброс при инвайте, исключении и блоке |
| Сессия | Состояние сокета на Gateway | Проверка в Auth один раз, на рукопожатии WSS. Ping в БД не ходит |
| Presence | Redis | Ключ устройства, TTL 120 с, запись не чаще раза в 60 с |
| Байты файла | Нигде в сервисах | Клиент читает бакет напрямую. Повторные 4.4 скачивания уже входят в трафик раздела 3 |

Хвост и состав группы нужны, чтобы 20_000 send/с и пик открытия приложения не упирались в Contact и в primary. Узел Message - 8 ГБ, страница истории - десятки килобайт; в памяти набор чатов, открытых сейчас, а не год архива. Промах кэша читает async-реплику шарда.
